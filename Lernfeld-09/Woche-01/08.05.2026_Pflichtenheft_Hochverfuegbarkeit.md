```

        ▼

```

## Kapitel 2: Grundkonzept der Server-Virtualisierung

### Was ist eine virtuelle Maschine (VM)?

```
SCHICHTEN-MODELL EINER VM:

  ┌───────────────────────────────────┐
  │  👤 Anwendung (SaaS-Plattform)    │  ← Läuft in der VM
  ├───────────────────────────────────┤
  │  💿 Gast-Betriebssystem (Windows  │  ← Eigenes OS der VM
  │       / Linux)                    │
  ├───────────────────────────────────┤
  │  ⚡ Hypervisor (VMware, Proxmox)  │  ← Verwaltet alle VMs
  ├───────────────────────────────────┤
  │  🔩 Physische Hardware            │  ← CPU, RAM, Festplatte
  │    (CPU, RAM, Disk, Netzwerk)     │
  └───────────────────────────────────┘
```

> 💡 **Einfach erklärt:** Eine VM ist wie ein **„Computer im Computer"**. Auf einem einzigen physischen Server können viele VMs gleichzeitig laufen – jede mit eigenem Betriebssystem und eigener Software.

### Wie löst Virtualisierung die Anforderungen?

#### 1. Hochverfügbarkeit durch Entkopplung

Weil die Software nicht mehr an eine bestimmte Hardware gebunden ist, kann eine VM bei einem Serverausfall **automatisch auf einen anderen Server verschoben werden** – in wenigen Sekunden, ohne dass der Kunde etwas merkt.

```
Server 1 fällt aus:

  VM Prod ──► automatisch verschoben ──► Server 2
              (Live-Migration, < 30 Sek.)
```

#### 2. Isolierte Testumgebung durch Klonen & Snapshots

```
Produktions-VM
      │
      ├─── Snapshot erstellen  ◄── "Foto" des aktuellen Zustands
      │
      └─── Klonen             ──► Test-VM (vollständig isoliert)
                                   • eigenes virtuelles Netzwerk
                                   • keine Verbindung zum Produktivsystem
                                   • in Minuten fertig
```

#### 3. Wartung ohne Ausfall

```
Wartungsablauf mit Virtualisierung:

  1. VM von Server 1  ──Live-Migration──►  Server 2  (VM läuft weiter!)
  2. Server 1 abschalten & warten
  3. VM zurück migrieren
     └── Kunden merken: nichts.
```

## Kapitel 3: Anforderungen an die neue Hardware

### Hardware-Virtualisierungsunterstützung (Pflicht!)

Neue Server **müssen** Prozessoren mit Hardware-Virtualisierung besitzen:

| Hersteller | Technologie | Funktion |
|------------|-------------|----------|
| 🔷 Intel | **VT-x** (Virtualization Technology) | CPU-Ebene VM-Unterstützung |
| 🟩 AMD | **AMD-V** (AMD Virtualization) | CPU-Ebene VM-Unterstützung |

### Warum ist das zwingend notwendig?

```
SOFTWARE-Virtualisierung vs. HARDWARE-Virtualisierung:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Merkmal            │ Software-Virt.     │ Hardware-Virt.
───────────────────┼───────────────────┼──────────────────
Performance        │ ❌ 20–40% Verlust │ ✅ < 5% Verlust
VM-Isolation       │ ⚠ Schwächer       │ ✅ Vollständig
Live-Migration     │ ❌ Nicht möglich  │ ✅ Möglich
Für SaaS geeignet  │ ❌ Nein           │ ✅ Ja
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

> ⚠ **Warum der aktuelle Server nicht ausreicht:**  
> Der vorhandene Server ist zu alt und besitzt keine Hardware-Virtualisierungsunterstützung. Selbst wenn man Software-Virtualisierung einsetzt, wäre **Live-Migration unmöglich** und die Performance unzureichend für eine produktive SaaS-Plattform.

## Kapitel 4: Konkreter technischer Lösungsvorschlag

### Systemaufbau im Überblick

```
                    👤 Kunden (Internet)
                           │
                           ▼
                  ┌─────────────────┐
                  │  ⚖ Load Balancer │
                  └────────┬────────┘
                   ┌───────┴───────┐
                   ▼               ▼
       ┌───────────────┐   ┌───────────────┐
       │  🖥 Server 1  │   │  🖥 Server 2  │
       │   (Primär)    │◄──►   (Failover)  │
       │               │   │               │
       │ ┌───────────┐ │   │ ┌───────────┐ │
       │ │ VM Prod A │ │   │ │ VM Prod A │ │
       │ │ VM Prod B │ │   │ │ VM Prod B │ │
       │ │ VM DB (P) │ │   │ │ VM DB (R) │ │
       └───────────────┘   └───────────────┘
              │         Live-Migration        │
              │         DB-Replikation        │
              └──────────────────────────────┘
                           │
              ┌────────────┴────────────┐
              │  💾 Zentraler Shared    │
              │    Storage (SAN/NAS)    │
              └─────────────────────────┘

       ┌─────────────────────────┐
       │  🔬 Server 3 (optional) │  ← Vollständig isoliertes
       │  Test-VMs               │    Test-Netzwerk
       └─────────────────────────┘
```

### Steckbrief der Lösung

| Komponente | Beschreibung | Zweck |
|------------|-------------|-------|
| **2 Produktionsserver** | Identische Hardware, Intel VT-x / AMD-V | Hochverfügbarkeit |
| **Hypervisor** | VMware vSphere, Proxmox VE oder Microsoft Hyper-V | VM-Verwaltung |
| **Load Balancer** | Verteilt Anfragen auf beide Server | Lastverteilung, kein Single Point of Failure |
| **Shared Storage (SAN/NAS)** | Zentraler Speicher, auf den beide Server zugreifen | Ermöglicht Live-Migration |
| **DB-Replikation** | Datenbank wird in Echtzeit auf Server 2 gespiegelt | Datenverlustschutz |
| **Test-Server (optional)** | Eigenes Netz, eigene VMs, kein Zugang zu Produktion | Sichere Testumgebung |

### Umsetzung der Lastenheft-Anforderungen

| Anforderung | Technische Maßnahme | Ergebnis |
|-------------|---------------------|---------|
| **99,99 % Verfügbarkeit** | 2-Server-Cluster + Live-Migration + Load Balancer | VM wechselt bei Ausfall in < 30 Sek. auf Server 2 |
| **Getrennte Testumgebung** | VM-Klon per Snapshot in separatem virtuellem Netz | Keine Verbindung zu Produktion möglich |
| **Wartung ohne Ausfall** | Live-Migration + Hot-Swap Hardware | Server 1 abschaltbar, VM läuft auf Server 2 weiter |

```
✅ 99,99 % Verfügbarkeit  →  2-Server-Cluster mit Live-Migration

```
